# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
dotnet build nfty.sln                       # build everything
dotnet test nfty.sln                        # run all tests
dotnet test tests/Nfty.Core.Tests           # one test project (also: tests/Nfty.Cli.Tests)
dotnet test --filter FullyQualifiedName~DnaTests           # one test class
dotnet test --filter FullyQualifiedName~DnaTests.Same_selection_same_dna   # one test method
dotnet run --project src/Nfty.Cli -- <command> [args]      # run the CLI
```

Targets **.NET 10**; tests are **xunit.v3** across all three projects, named `Snake_case_sentences` (`Same_selection_same_dna`), which is what the `--filter` above must match. There is no separate lint step because the build is one: `Directory.Build.props` sets `TreatWarningsAsErrors` and `GenerateDocumentationFile`, so a warning or an undocumented public member fails the build. Package versions live in `Directory.Packages.props`, never in a csproj. ImageSharp is pinned to **3.1.11** on purpose (4.0.0 requires a build-time license key) — do not upgrade it. `sixlabors.lic` is gitignored and account-specific; never commit it.

## Big picture

`nfty` generates NFT-style asset collections by stacking layered PNGs, with a twist: each layer has one of three **kinds** (`LayerKind`). **Dynamic** and **static** layers are grayscale *value-maps* colorized at generation time — recoloring preserves each pixel's value/lightness and injects hue+saturation, so the output space is far larger than the source images; dynamic **rolls** its color per asset from a weighted colorization, while static applies a **single fixed color** deterministically (no RNG). **Custom** layers are full-color RGBA images composited **as-is**, never colorized (`Colorization` must be null).

**The domain is a cooking metaphor — learn these six terms before touching the model:**

| Term | File ext | What it is | Owns |
|------|----------|-----------|------|
| **CookBook** | `.cbk` | An *uncooked Set* — the top-level container | Canvas dimensions, collection metadata, per-Recipe selection weights |
| **Recipe** | `.rcp` | A complete template for one character/image *type* | Ordered layer stack (`layerOrder`, bottom-to-top — **the** paint order), incompatibility rules |
| **Ingredient** | `.igt` | One layer / trait-category | `kind` (dynamic/static/custom), colorization config, its weighted variant images |
| **Variant** | *(inside `.igt`)* | One image + weight + name | A single PNG; not its own file — hidden behind the Ingredient |
| **Set** | `.set` or folder | The generated (cooked) output | Images + per-item metadata + rarity + seed |
| **Kitchen** | `.ktn` | The top-level *workspace* — names the folder it sits in | Its own identity only; membership is **discovered** by scanning that folder, never recorded (see `docs/superpowers/specs/2026-08-04-kitchen-design.md`) |

This is **"Model A"**: a CookBook is a container of whole-template Recipes, and generating it produces a *mixed* Set by rolling a Recipe per asset. (An older "Model B" where Recipe = one layer was abandoned — ignore any stray references to it.) All images share one size, fixed by the **CookBook canvas** — the single source of truth for dimensions; every variant is validated against it.

Every archive (`.cbk`/`.rcp`/`.igt`/`.set`/`.ktn`) is just a **ZIP with a `manifest.json`** plus nested files; the custom extension is a renamed `.zip`, so any unzip tool can inspect it. `.cbk` nests `.rcp`s nests `.igt`s, so the archive layers mirror the domain layers. Every manifest implements `ISchemaVersioned` and is version-checked in `ArchiveIo.ReadManifest` — the one place all manifests are read — so an unreadable version raises `UnsupportedSchemaVersionException` rather than silently misparsing. The gate accepts `Schema.Oldest..Schema.Current` and refuses anything **newer**: a future field this build cannot see could change what the archive means. It used to demand exact equality, which made the format unevolvable — bumping `Current` by one would have orphaned every archive ever written. Reading older is sound only because of a contract you must keep: **every field added after v1 is optional and defaults to "absent"**. A rename, a changed meaning or a new *required* field breaks that and needs real migration, not a bump. An additive optional field (like `TargetSupply`) needs **no** bump at all — `System.Text.Json` ignores unknown properties, so older builds still read it, whereas bumping would make them reject it. Extensions map to types via `Archives.KindOf`, which rejects an unknown extension rather than guessing.

### Generation pipeline (`Generation/Generator.cs`)

Per asset: **roll recipe** (by cookbook weight) → **roll each layer's variant** (by ingredient weight) → **apply the recipe's incompatibility rules** (re-roll on violation, bounded retry budget) → **colorize dynamic/static layers** (custom composites as-is) → **composite** → **hash DNA** → **dedup** (re-roll on collision) → **emit**.

- **Determinism:** a single string seed drives a **SplitMix64** RNG (`Rng.cs`), recorded in the Set. Same cookbook + same seed ⇒ byte-identical output — across machine locales *and* CPU architectures. Two things guard this: every sort that reaches an output file uses `StringComparer.Ordinal` (a default `OrderBy` sorts by current culture and silently breaks it), and `SeedHash.ToUlong` reads the seed's SHA-256 with `BinaryPrimitives.ReadUInt64LittleEndian` rather than native-endian `BitConverter` (which would seed the RNG differently on a big-endian CPU). Little-endian was chosen so the fix changes no output ever produced on the little-endian machines every Set was generated on.
- **DNA** (`Dna.cs`): SHA-256 over the recipe id + each layer's variant id, plus — for dynamic (rolled) and static (fixed) layers — the `(H,S)` **quantized** per that layer's config (custom layers contribute variant id only). Quantizing folds the explosive color space into uniqueness. Duplicate DNA ⇒ re-roll. Two distinct failures, never conflated: `RuleConflictException` when a recipe's rules exclude *every* combination (the space is empty), and `UniqueSpaceExhaustedException` when the space is real but smaller than `N`. The latter states the true maximum, counted by `UniqueSpace.Count` (`Generation/UniqueSpace.cs`) — legal variant combinations honouring rules, times each dynamic layer's quantized `(H,S)` buckets; static/custom contribute one bucket each. It enumerates only when the unconstrained product fits under a cap (default 1M) and otherwise saturates, reporting `IsExact = false` (i.e. "more than N" — then the reroll budget ran out, not the space). **The count is a promise:** exactly `Total` unique DNA must be generable, so bucket counting must track `ColorRoller.Roll` exactly — it samples `Min + r*(Max-Min)` with `r ∈ [0,1)`, making a range **half-open** `[Min, Max)`; only a degenerate `Min == Max` reaches its endpoint. Off-by-one here makes `Generate` throw the self-contradicting "allows exactly N, but N were requested".
- **Extend** (`extend` command / `SetWriter.ReadExisting`): re-opens an existing Set, loads its DNAs + numbering, rolls only new non-colliding assets, and **recomputes rarity across the whole collection** (rewriting existing items' `rarity` field) since rarity is collection-wide. Extend is not a second pipeline — it is the same `Generator.Generate` call with its `existingDnas` / `startNumber` parameters supplied. Keep new work behind that seam rather than forking the generator.
- **Depth is `layerOrder` read a second way, never a stored field.** `Editing/LayerDepth.cs` projects it: depth is the **1-based position, dense, bottom-first — depth 1 paints first and sits furthest back**. `MoveTo`/`MoveBy` clamp (nudging the top layer up is a no-op the UI shouldn't guard); `At` **throws** (asking what sits at depth 7 of a five-layer stack is a caller bug). A stored integer `z` was considered and rejected: it would make two layers at one depth *expressible*, which is the collision an author wants prevented, and would need an absent-default on every read path for every `schemaVersion: 1` archive. A list makes the illegal state unrepresentable rather than merely invalid. Reordering preserves the exact id set, so `Validator`'s bijection survives every move — and `Validator` gains **nothing** for depth, because those bijection rules already *are* the depth invariant.
- **Reordering a book produces a different collection, not a re-render.** `Dna.Compute` sorts selections ordinally, so a *given selection* hashes the same in any order — that is what makes a reorder safe for already-minted Sets, and why depth must never enter the hash. But `Generator.RollOne` walks the layers in `layerOrder` consuming one `WeightedRoller.Roll` each, so moving a layer moves **which RNG draw reaches it**: on any layer with more than one variant the selection itself changes. Same seed + reordered book ⇒ different pixels *and* different identities. Only `set.json`'s `cookbookSha256` records it, which is why `extend` warns (to stderr, never refusing) when the book's hash differs from the one the Set recorded — and why a null on either side means "cannot tell" rather than "they differ".
- `Generator.Generate` runs `Validator.Validate` itself and throws if it reports **any** problem, so callers need not pre-validate; the `validate` command exists for humans, not as a required pre-step. `Validator` is the single place that decides what a legal cookbook is — it must **report** problems, never throw, since `validate` (and a GUI's "what's wrong?") exists precisely to explain a broken book. Check id uniqueness before any `ToDictionary` that would throw on a duplicate. A layer's **name** must also be unique within its recipe: the name is the `trait_type` the layer is published under, so two layers sharing one merge into a single trait and a single rarity bucket — which is how a collection ships percentages above 100. The reserved-name check for `"Type"` is the special case of that rule.

### Project layout

- **`Nfty.Core`** — the entire engine, organized by concern so the planned Avalonia GUI can consume it directly:
  - `Model/` — immutable domain records (manifests, variants, rules, colorization).
  - `Formats/` — ZIP + manifest readers/writers (`ArchiveIo` is the shared low-level helper), plus `Validator`.
    - **Manifest ≠ what the engine consumes.** `Loaded.cs` defines `LoadedCookBook`/`LoadedRecipe`/`LoadedIngredient`, each pairing a `Model/` manifest record with its eagerly-decoded `Image<Rgba32>` variants. `Generator` and `Validator` take `Loaded*`, never bare manifests — so reading an archive is also what pulls every PNG into memory.
    - **All manifest JSON goes through `Json.Options`** (camelCase properties, enums as camelCase strings). Serializing a manifest with default options silently breaks round-trips; reuse the shared options for any new manifest field.
  - `Imaging/` — color conversion, color-spec parsing, value-map colorization, compositing (ImageSharp), and `VariantPreview` — the render one Variant gets *exactly as generation would*. That rule lives here, not in a front-end, because the CLI's `preview` and the GUI's Export must produce the identical file; two copies is how that stops being true. Above it sit `StackPreview` (several layers at their real depths, split around the one being edited) and `StackRoll` (a whole Recipe rolled into that stack, in generation's own draw order). Both build on `VariantPreview` + `Compositor` and add **no third rendering path**. "Exactly" is meant literally: a `PreviewLayer` carries the unrounded rolled `(H,S)` **alongside** its colour spec and draws from the former, because every spec resolves through 8-bit RGB and a rolled hue between two representable colours cannot be spelled — rendering through the string put the preview ~0.25° off the asset. The spec stays for humans to read and re-run.
  - `Generation/` — RNG, weighted roller, color roller, DNA, rules engine, orchestrator.
  - `Output/` — dual per-item metadata (standards-pure OpenSea `metadata/NNNN.json` + rich `nfty/NNNN.json` with dna/seed/rarity/per-layer color) + set writer + extend loader. `set.json` records `cookbookSha256` — the hash of the source `.cbk`, carried on `LoadedCookBook.SourceSha256` (populated by `CookBookArchive.Read`, **null for an in-memory book that never came from a file**) → `GeneratedSet` → `SetManifest`. It is what ties a Set back to the exact archive that produced it, so keep it threaded through.
  - `Stats/` — rarity computation, plus the text reports the CLI prints (`CollectionReport`, `IdentityReport`, `KitchenReport`, and **`VoxelReport`** — which variants carry *partial* alpha, the one thing a voxel converter cannot resolve; partial alpha is legal, so that is a **report and never a `Validator` problem**, and it is opt-in via `inspect --voxel` because it costs a full scan of every variant image). Rendered here so the GUI shows byte-identical text rather than something similar. Reports format **invariant** — they get copied and compared across machines — and degrade to a line rather than throwing when a book's DNA space cannot be counted.
- **`Nfty.Cli`** — thin `System.CommandLine` wiring. Command definitions live in `CommandFactory.cs` (authoring commands in the `CommandFactory.Authoring.cs` partial); `Program.cs` just invokes it. Commands: `inspect` (any of the four archive kinds, including a `.ktn`, which it lists), `validate`, `stats`, `preview`, `generate`, `extend`, plus authoring — `new ingredient|recipe|cookbook|kitchen`, `add variant|ingredient|recipe`, and `move ingredient` (manifest JSON + PNGs, resolved by the `{id}.png`→`{id}.igt`→`{id}.rcp` convention; `Validator.ValidateIngredient`/`ValidateRecipe` gate the per-level builds). `inspect` also prints a book's own **palette** (the swatches an archive carries, so a collection handed on brings its colours with it) and takes **`--voxel`**, refused on a `.ktn` — a Kitchen lists paths without opening them, and an option that silently does nothing is worse than one that says no. `preview` takes **either** an `.igt` (one variant, `--variant`/`--color`) **or** a `.rcp` (the whole stack, `--seed`/`--only`/`--with`), dispatched by `Archives.KindOf`; options belonging to the other form are **rejected**, never ignored. A `.rcp` has no canvas of its own, so the recipe form takes the size `Validator.ValidateRecipe` has already proved every variant shares — deliberately not a `--canvas` flag, which would render a preview at a size no CookBook could cook at.

**Errors surface through `ErrorReport.Format`, not raw traces.** `Program.cs` sets `EnableDefaultExceptionHandler = false` — without it `System.CommandLine` catches first and prints `Unhandled exception:` plus a trace, and `Program`'s own handler never runs. Commands themselves catch nothing: they throw, and `Program` prints the message (plus the trace only under the recursive `--verbose`) and returns 1. Engine exceptions are expected to carry a message worth showing a user verbatim — that is why `ErrorReport` prints `ex.Message` rather than the type name. `Nfty.Cli.Tests` covers `ErrorReport` and that the command surface parses; engine behavior is covered in `Nfty.Core.Tests`, so put real assertions there.

**Callers own image disposal.** `Nfty.Core` returns live `Image<Rgba32>` objects. This covers **both directions**: reading an archive eagerly decodes every variant PNG, so `LoadedCookBook`/`LoadedRecipe`/`LoadedIngredient` are `IDisposable` too and each disposes what it owns down to the variant images — `using var book = CookBookArchive.Read(path)` frees the whole tree, and a GUI that opens and closes cookbooks must do so. On the output side, `GeneratedAsset` and `GeneratedSet` are `IDisposable` (disposing the set disposes every asset image), so `using var set = Generator.Generate(...)` is the default — see `generate`/`extend` in `CommandFactory.cs`. `Generate` materialises the whole collection in memory; a consumer that can't afford that (a GUI grid over 10k assets) should use **`Generator.GenerateStreaming`**, which yields one asset at a time and hands ownership of each to the caller — an abandoned enumeration leaves the last asset undisposed.

### Sync/async pairs

Every I/O entry point has an async twin; `Generate` also takes an optional `IProgress<GenerationProgress>` and `CancellationToken` (`SetWriter.WriteAsync` reports `WriteProgress`). The split is deliberate and worth preserving:

- **Genuinely async** (real awaits on stream/JSON/PNG-codec work): `CookBookArchive`/`RecipeArchive`/`IngredientArchive` `ReadAsync`/`WriteAsync`, `SetWriter.WriteAsync`/`ReadExistingAsync`. Note `ZipArchive`'s own directory parsing has no async API — only the per-entry I/O awaits.
- **CPU-bound, offloaded**: `Generator.GenerateAsync` is a `Task.Run` over the sync core. Rolling/colorizing/compositing has nothing to await; it exists to keep a UI thread free. **Don't add fake `async` to the generation loop** — put new work behind the progress/cancellation parameters instead.

### Color specs

Anywhere a user enters a color it must carry an explicit prefix — `hex:`, `rgb:`, `hsl:`, or `hsv:` (e.g. `hex:d6249f`, `hsv:322,83,84`). A missing/unknown prefix is a **validation error, never guessed** (`Imaging/ColorSpec.cs`). For dynamic/static colorization only `H`/`S` are taken from the color; value/lightness comes from the grayscale value-map.

## Conventions

- **PR-per-task, one fresh agent per major task.** Work lands on a local feature branch merged into `main` — see `docs/superpowers/` for the design spec and implementation plans. **The spec (`docs/superpowers/specs/`) wins over the plan docs (`docs/superpowers/plans/`)**, which are stale — they predate the Custom kind and describe a two-kind `LayerKind`. Where the shipped archives contradict even the spec, the archives win: `schemaVersion: 1` is out in the world, so the doc gets corrected, not the format.
- The **Avalonia GUI** is the second front-end (cross-platform incl. mobile), built on `Nfty.Core`; design mockups live in `docs/design/mockups/` — `explorer.html` (the primary screen), `landing.html` (the pre-open default view), `help.html` (the quick-reference view), the three `wizard-*.html`, and `ingredient-editor.html`. Their style is **locked** and they are the 1:1 reference, so a new hex literal in any of them means the design has drifted. **Never edit a mockup to match the app** — the app moves. Note the token blocks are **not** identical across the seven (`gallery.html` is a generated index, not a screen): `explorer.html`, `help.html` and `ingredient-editor.html` carry the full set, while `landing.html` and the three `wizard-*.html` carry a trimmed one — no sans font token (those four screens are entirely mono, which the app reproduces via a `monoform` class), and no shadow, guide or radius tokens. Compare a value against the file you are implementing, not against whichever mockup you read first. Keep `Nfty.Core` free of UI/CLI dependencies so both front-ends can share it.

### GUI: state and house rules

The visual-polish work is merged into `main`. **`docs/superpowers/specs/2026-08-02-gui-visual-polish-status.md` is the running handoff** — which of the 12 audit slices are done, what is deliberately left open, and why. Read it plus `2026-08-01-nfty-gui-visual-audit.md` before touching the GUI.

- **Verify visuals from a rendered frame, never from the markup.** `NFTY_CAPTURE=1 NFTY_CAPTURE_DIR=<dir> dotnet test tests/Nfty.App.Tests --filter FullyQualifiedName~VisualCapture`, then *look at* the PNGs. Page frames render at **1180x720** — the mockups' own units, which is what a page's layout is authored against; the pane track alone needs 1014px, so a smaller capture makes correct layouts look clipped. The **shell** frame is captured at **1416x864** instead, because the whole shell renders at `ShellViewModel.BaseScale` (1.2) and that is MainWindow's real size. Nearly every defect in this branch was found this way and would have been missed by reading code.

  Two companion tests catch what a frame can't. `DarkModeContrastTests` walks every screen in both themes and scores each text run against the surface it actually lands on, compositing alpha through translucent ancestors — it found "1 problem" rendering as opaque Black at 1.14:1, in the invalid-CookBook state no fixture had ever built. `ThemeResourceTests.Every_dynamic_resource_the_markup_references_resolves_in_both_themes` derives its key list from the markup rather than a hand-written list, because that bug's cause was `WarningBrush` being referenced and defined nowhere — **an unresolved `DynamicResource` does not throw; the property silently keeps its default.**
- **The harness must render the shipped control, never a replica.** The shell chrome lives in `Nfty.App/Views/ShellChromeView.axaml` rather than in the desktop head specifically so the capture can reach it — a hand-written mirror had been drifting from the real titlebar with nothing to detect it.
- **Token brushes only in Views.** No raw hex outside `Themes/Tokens.axaml`; a new colour goes in **both** dictionaries. Avalonia hex is `#AARRGGBB` — the mockup CSS is `#RRGGBBAA`, so alpha moves to the front. **A gradient must be a whole brush per theme dictionary**, never a `LinearGradientBrush`/`RadialGradientBrush` built inside a `Style` `Setter` with `DynamicResource` stops: that brush is constructed once and shared, so its stops never re-resolve on a theme change. It shipped the CookBook identity card painting its light gradient in dark mode, and is invisible in light mode, in the markup, and to any single-theme test. `ThemedGradientTests` guards it.
- **Geometry is fixed: reserve the space, toggle the ink.** A control appearing or disappearing must not move, resize or reflow anything around it — a table is the same width locked and unlocked, a row the same height active and inactive, at every window size. Use `Opacity`/`IsHitTestVisible`, **never** `IsVisible`, on anything that occupies layout, and fixed column definitions rather than `Auto` where the content can vanish. Prove it by pixel-diffing two captured frames, not by eye. The knowing exception on record: the always-present grip column gives the locked Layers table a 26px gutter `explorer.html` does not draw, accepted because the locked set has no reorder affordance at all.
- **A pointer-drag gesture is pointer capture, not `DragDrop.DoDragDropAsync`.** The latter needs a platform drag *source* and `Avalonia.Headless` registers none — `IPlatformDragSource` is absent from the assembly, and a call under the harness never returns. It would also make the gesture uncapturable and untestable, against the rule above it. And **drag always ships with a keyboard path** (`Alt+Up`/`Alt+Down` over `LayerDepth.MoveBy`); pointer-only reorder is an incomplete feature, not a scoped-down one. Note `ObservableCollection.Move` makes `ItemsControl` **drop and recreate** the moved container, so focus must be restored at `DispatcherPriority.Loaded`, behind the layout pass — without it the second keystroke is silently swallowed.
- **Avalonia is 12.1.1**, on .NET 10. `Grid.ColumnSpacing`/`RowSpacing` and control-level `LetterSpacing` exist — use them rather than per-child margins or a TextBlock-inside-Button. All three test projects run on **xunit.v3**; `Avalonia.Diagnostics` is now `AvaloniaUI.DiagnosticsSupport`, and the text shaper is opt-in via `Avalonia.HarfBuzz`.
- **Icons** are `StreamGeometry` in `Themes/Icons.axaml`, traced from the mockups' SVG and authored in their 24-unit box. `Path.ico` maps that box onto the icon box the way an `<svg viewBox>` does (`Stretch="None"` + `scale(size/24)`), so every glyph shares one scale. Never set `Width`/`Height` on a `Path.ico` inline — use the `xs`/`sm`/`ti`/`lg` classes, which carry the matching transform.
- **Fluent fights back, and the fights are documented where they happen.** Style ordering is last-one-wins at equal specificity, so a narrower opt-out must be declared *after* the blanket rule. A selector may cross only **one** `/template/` boundary — reaching a nested control's internals needs its own `ControlTheme`. Neutralising a Fluent state means setting it **explicitly** (e.g. `Transparent`); simply not painting hands the state back to Fluent's stock blue. Some geometry (spinner column, slider track) is fixed inside Fluent's templates at a priority a `Style` setter cannot beat — where that happens the setters were **removed** and the gap commented, rather than left in place looking effective.
- **Pixel art scales with nearest neighbour, never a filter.** Every image the app shows is generated pixel art displayed at a size unrelated to its pixel count, so each view root that hosts an `<Image` sets `RenderOptions.BitmapInterpolationMode="None"`. It cannot be a `Style` `Setter`: Avalonia 12's `RenderOptions` is a Get/Set pair, not an `AvaloniaProperty`. `PixelPerfectRenderingTests` derives its view list from the markup and reads the **effective** mode off live controls, because the value is composited at draw time and a child reads `Unspecified`. Nothing in `Nfty.Core` resamples, blurs or anti-aliases either — commands write whole pixels and import refuses a wrong-sized image rather than scaling it. Partial alpha is unrelated: a value the author opts into, not a filter.
- **Width is a budget, and an overrun is silent.** A `Grid` star column whose siblings outgrow the pane is arranged at **zero width** — no exception, no warning, the content simply is not there (it shipped that way in the palette strip's first cut, with a correct ViewModel behind it). A clipped control still reports its own non-zero `Bounds`, so assert **containment** inside the parent, not `Bounds.Width > 0`. `PaletteStripLayoutTests` is the pattern.
- **A `$parent[…]` binding from inside a `ContextMenu` never resolves** — a ContextMenu is not in the visual tree — and fails silently, taking the whole item template with it. Hand the item its own command instead (`PaletteSwatch.ForgetCommand`), and exempt it in `WiringCoverageTests` with the reason.
- **The app dims disabled controls to 0.38 opacity**, which is legible over a full-strength foreground and *not* over an already-muted one (`DarkModeContrastTests` floor is 2.0). Don't disable muted text; swap the ink inside a fixed-size cell instead.
- **Tests must never read or write the real `%APPDATA%`** — inject a temp directory into `RecentsService`.
- When changing behavior, mirror the existing test style: seeded **distribution** tests for rollers, **exact-pixel** tests for colorization *and* compositing, and **round-trip** tests for archives. There are **no golden-image files** — every image assertion reads a pixel off a tiny synthetic image, so keep new imaging tests self-contained rather than introducing a golden-file harness.
- **Tests build their fixtures in memory** — each test file constructs `Loaded*` graphs directly (see `GeneratorTests.Ing`/`Recipe`/`OneRecipeBook`) from 1×1 or 2×2 solid-fill `Image<Rgba32>`s, with private per-file builders shaped for what that file tests (weights in `RarityCalculatorTests`, kinds in `KindSemanticsTests`). Tests that touch the filesystem use `Directory.CreateTempSubdirectory()`.
- **`tests/fixtures/` is the one exception**, and the only place real archives are read from disk (`FixtureArchiveTests`). `VaporPets.cbk` + its `cat.rcp`/`aura.igt` parts exercise all three layer kinds and an exclude rule in one 8×8 archive. **Their value is that an older build wrote them and they still read** — so don't regenerate them to make a failing fixture test pass; that launders a format change instead of catching it. A deliberate format change means bumping `Schema.Current` and adding a new fixture beside this one. The images are synthetic placeholders, to be joined (not replaced) by real art. See `tests/fixtures/README.md`.
