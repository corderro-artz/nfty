# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
dotnet build nfty.sln                       # build everything
dotnet test nfty.sln                        # run all tests
dotnet test tests/Nfty.Core.Tests           # one test project (also: tests/Nfty.Cli.Tests)
dotnet test --filter FullyQualifiedName~DnaTests           # one test class
dotnet test --filter FullyQualifiedName~DnaTests.Same_selection_same_dna   # one test method
dotnet run --project src/Nfty.Cli -- <command> [args]      # run the CLI
```

Targets **.NET 10**; tests are **xunit.v3** across all three projects, named `Snake_case_sentences` (`Same_selection_same_dna`), which is what the `--filter` above must match. There is no separate lint step because the build is one: `Directory.Build.props` sets `TreatWarningsAsErrors` and `GenerateDocumentationFile`, so a warning or an undocumented public member fails the build. Package versions live in `Directory.Packages.props`, never in a csproj. ImageSharp is pinned to **3.1.11** on purpose (4.0.0 requires a build-time license key) — do not upgrade it. `sixlabors.lic` is gitignored and account-specific; never commit it.

## Big picture

`nfty` generates NFT-style asset collections by stacking layered PNGs, with a twist: each layer has one of three **kinds** (`LayerKind`). **Dynamic** and **static** layers are grayscale *value-maps* colorized at generation time — recoloring preserves each pixel's value/lightness and injects hue+saturation, so the output space is far larger than the source images; dynamic **rolls** its color per asset from a weighted colorization, while static applies a **single fixed color** deterministically (no RNG). **Custom** layers are full-color RGBA images composited **as-is**, never colorized (`Colorization` must be null).

**The domain is a cooking metaphor — learn these six terms before touching the model:**

| Term | File ext | What it is | Owns |
|------|----------|-----------|------|
| **CookBook** | `.cbk` | An *uncooked Set* — the top-level container | Canvas dimensions, collection metadata, per-Recipe selection weights |
| **Recipe** | `.rcp` | A complete template for one character/image *type* | Ordered layer stack (`layerOrder`, bottom-to-top — **the** paint order), incompatibility rules |
| **Ingredient** | `.igt` | One layer / trait-category | `kind` (dynamic/static/custom), colorization config, its weighted variant images |
| **Variant** | *(inside `.igt`)* | One image + weight + name | A single PNG; not its own file — hidden behind the Ingredient |
| **Set** | `.set` or folder | The generated (cooked) output | Images + per-item metadata + rarity + seed |
| **Kitchen** | `.ktn` | The top-level *workspace* — names the folder it sits in | Its own identity only; membership is **discovered** by scanning that folder, never recorded (see `docs/superpowers/specs/2026-08-04-kitchen-design.md`) |

This is **"Model A"**: a CookBook is a container of whole-template Recipes, and generating it produces a *mixed* Set by rolling a Recipe per asset. (An older "Model B" where Recipe = one layer was abandoned — ignore any stray references to it.) All images share one size, fixed by the **CookBook canvas** — the single source of truth for dimensions; every variant is validated against it.

Every archive (`.cbk`/`.rcp`/`.igt`/`.set`/`.ktn`) is just a **ZIP with a `manifest.json`** plus nested files; the custom extension is a renamed `.zip`, so any unzip tool can inspect it. `.cbk` nests `.rcp`s nests `.igt`s, so the archive layers mirror the domain layers. Every manifest implements `ISchemaVersioned` and is version-checked in `ArchiveIo.ReadManifest` — the one place all manifests are read — so an unreadable version raises `UnsupportedSchemaVersionException` rather than silently misparsing. The gate accepts `Schema.Oldest..Schema.Current` and refuses anything **newer**: a future field this build cannot see could change what the archive means. It used to demand exact equality, which made the format unevolvable — bumping `Current` by one would have orphaned every archive ever written. Reading older is sound only because of a contract you must keep: **every field added after v1 is optional and defaults to "absent"**. A rename, a changed meaning or a new *required* field breaks that and needs real migration, not a bump. An additive optional field (like `TargetSupply`) needs **no** bump at all — `System.Text.Json` ignores unknown properties, so older builds still read it, whereas bumping would make them reject it. Extensions map to types via `Archives.KindOf`, which rejects an unknown extension rather than guessing.

### Generation pipeline (`Generation/Generator.cs`)

Per asset: **roll recipe** (by cookbook weight) → **roll each layer's variant** (by ingredient weight) → **apply the recipe's incompatibility rules** (re-roll on violation, bounded retry budget) → **colorize dynamic/static layers** (custom composites as-is) → **composite** → **hash DNA** → **dedup** (re-roll on collision) → **emit**.

- **Determinism:** a single string seed drives a **SplitMix64** RNG (`Rng.cs`), recorded in the Set. Same cookbook + same seed ⇒ byte-identical output — across machine locales *and* CPU architectures. Two things guard this: every sort that reaches an output file uses `StringComparer.Ordinal` (a default `OrderBy` sorts by current culture and silently breaks it), and `SeedHash.ToUlong` reads the seed's SHA-256 with `BinaryPrimitives.ReadUInt64LittleEndian` rather than native-endian `BitConverter` (which would seed the RNG differently on a big-endian CPU). Little-endian was chosen so the fix changes no output ever produced on the little-endian machines every Set was generated on.
- **DNA** (`Dna.cs`): SHA-256 over the recipe id + each layer's variant id, plus — for dynamic (rolled) and static (fixed) layers — the `(H,S)` **quantized** per that layer's config (custom layers contribute variant id only). Quantizing folds the explosive color space into uniqueness. Duplicate DNA ⇒ re-roll. Two distinct failures, never conflated: `RuleConflictException` when a recipe's rules exclude *every* combination (the space is empty), and `UniqueSpaceExhaustedException` when the space is real but smaller than `N`. The latter states the true maximum, counted by `UniqueSpace.Count` (`Generation/UniqueSpace.cs`) — legal variant combinations honouring rules, times each dynamic layer's quantized `(H,S)` buckets; static/custom contribute one bucket each. It enumerates only when the unconstrained product fits under a cap (default 1M) and otherwise saturates, reporting `IsExact = false` (i.e. "more than N" — then the reroll budget ran out, not the space). **The count is a promise:** exactly `Total` unique DNA must be generable, so bucket counting must track `ColorRoller.Roll` exactly — it samples `Min + r*(Max-Min)` with `r ∈ [0,1)`, making a range **half-open** `[Min, Max)`; only a degenerate `Min == Max` reaches its endpoint. Off-by-one here makes `Generate` throw the self-contradicting "allows exactly N, but N were requested".
- **Extend** (`extend` command / `SetWriter.ReadExisting`): re-opens an existing Set, loads its DNAs + numbering, rolls only new non-colliding assets, and **recomputes rarity across the whole collection** (rewriting existing items' `rarity` field) since rarity is collection-wide. Extend is not a second pipeline — it is the same `Generator.Generate` call with its `existingDnas` / `startNumber` parameters supplied. Keep new work behind that seam rather than forking the generator.
- **Depth is `layerOrder` read a second way, never a stored field.** `Editing/LayerDepth.cs` projects it: depth is the **1-based position, dense, bottom-first — depth 1 paints first and sits furthest back**. `MoveTo`/`MoveBy` clamp (nudging the top layer up is a no-op the UI shouldn't guard); `At` **throws** (asking what sits at depth 7 of a five-layer stack is a caller bug). A stored integer `z` was considered and rejected: it would make two layers at one depth *expressible*, which is the collision an author wants prevented, and would need an absent-default on every read path for every `schemaVersion: 1` archive. A list makes the illegal state unrepresentable rather than merely invalid. Reordering preserves the exact id set, so `Validator`'s bijection survives every move — and `Validator` gains **nothing** for depth, because those bijection rules already *are* the depth invariant.
- **Reordering a book produces a different collection, not a re-render.** `Dna.Compute` sorts selections ordinally, so a *given selection* hashes the same in any order — that is what makes a reorder safe for already-minted Sets, and why depth must never enter the hash. But `Generator.RollOne` walks the layers in `layerOrder` consuming one `WeightedRoller.Roll` each, so moving a layer moves **which RNG draw reaches it**: on any layer with more than one variant the selection itself changes. Same seed + reordered book ⇒ different pixels *and* different identities. Only `set.json`'s `cookbookSha256` records it, which is why `extend` warns (to stderr, never refusing) when the book's hash differs from the one the Set recorded — and why a null on either side means "cannot tell" rather than "they differ".
- `Generator.Generate` runs `Validator.Validate` itself and throws if it reports **any** problem, so callers need not pre-validate; the `validate` command exists for humans, not as a required pre-step. `Validator` is the single place that decides what a legal cookbook is — it must **report** problems, never throw, since `validate` (and a GUI's "what's wrong?") exists precisely to explain a broken book. Check id uniqueness before any `ToDictionary` that would throw on a duplicate. A layer's **name** must also be unique within its recipe: the name is the `trait_type` the layer is published under, so two layers sharing one merge into a single trait and a single rarity bucket — which is how a collection ships percentages above 100. The reserved-name check for `"Type"` is the special case of that rule.

### The user manual (`docs/manual/`, `mkdocs.yml`)

A Material for MkDocs site, organized on **Diátaxis**: `Get started` (tutorials — linear, one path), `How do I…` (how-to — titled by the reader's *goal*, never by a feature name), `How nfty works` (explanation — "why", no steps), `Reference` (austere description, mirrors the product). A page belongs to exactly one of those four; the previous manual mixed all four inside single pages and had **two** cross-links in fourteen files.

- **The theme is `Tokens.axaml` in CSS.** `docs/manual/stylesheets/vaporsoft.css` carries no invented colors. Two translation traps are commented where they bite: Avalonia hex is `#AARRGGBB` and CSS is `#RRGGBBAA`, and Material's `--md-primary-fg-color` is the header *background*.
- **A screenshot is a pair, and the pair is switched by Material, not by you.** `thing-light.png#only-light` + `thing-dark.png#only-dark`. Material hides the off-theme half with `[data-md-color-scheme="slate"] img[src$="#only-light"] { display: none }` — the same specificity as `.md-typeset img[src*="/images/"]`, and `extra_css` loads *after* Material's sheet, so setting `display` there wins a tie it should never enter and renders both images stacked. Never set `display` on a figure rule.
- **The figures come from the running app, not from `VisualCapture`.** `tools/docs-capture/` regenerates them: it draws real 64×64 art, assembles a real CookBook (five layers, all three kinds, a rule, ~900k unique DNA), and captures the live window in both themes. The harness fixtures are 8×8 solid fills and produce a manual full of empty panels quoting "2 unique DNA". Its README carries the PowerShell traps — `$h` silently clobbering an `-H` parameter, and a blind `Ctrl+T` that yields the same theme twice.
- `docs_dir` is `docs/manual`, **not** `docs/` — otherwise MkDocs copies the archived design mockups and the superpowers specs into the published site. `includes/` is `exclude_docs`'d because it is a snippet fragment, and `pymdownx.snippets` needs `base_path: [docs/manual]` since it defaults to the **project root** and otherwise resolves to nothing in silence.
- `navigation.sections` renders a top-level group as a plain label, which cannot also be the link to that section's index page — so it is off, and `navigation.indexes` makes each section title clickable.

### Project layout

- **`Nfty.Core`** — the entire engine, organized by concern so the planned Avalonia GUI can consume it directly:
  - `Model/` — immutable domain records (manifests, variants, rules, colorization).
  - `Formats/` — ZIP + manifest readers/writers (`ArchiveIo` is the shared low-level helper), plus `Validator`.
    - **Manifest ≠ what the engine consumes.** `Loaded.cs` defines `LoadedCookBook`/`LoadedRecipe`/`LoadedIngredient`, each pairing a `Model/` manifest record with its eagerly-decoded `Image<Rgba32>` variants. `Generator` and `Validator` take `Loaded*`, never bare manifests — so reading an archive is also what pulls every PNG into memory.
    - **`ArchivePeek` reads a manifest without decoding anything.** `Loaded*` is the engine's
      form and pulls every PNG into memory; a *listing* needs neither. `RecipeWeights.Count` and
      `Canvas` are in the outer manifest, so a workspace row can say "3 recipes · 1000×1000"
      without a nested read. It goes through the same `ArchiveIo.ReadManifest` gate, so the
      schema check still applies.
    - **All manifest JSON goes through `Json.Options`** (camelCase properties, enums as camelCase strings). Serializing a manifest with default options silently breaks round-trips; reuse the shared options for any new manifest field.
  - `Imaging/` — color conversion, color-spec parsing, value-map colorization, compositing (ImageSharp), and `VariantPreview` — the render one Variant gets *exactly as generation would*. That rule lives here, not in a front-end, because the CLI's `preview` and the GUI's Export must produce the identical file; two copies is how that stops being true. Above it sit `StackPreview` (several layers at their real depths, split around the one being edited) and `StackRoll` (a whole Recipe rolled into that stack, in generation's own draw order). Both build on `VariantPreview` + `Compositor` and add **no third rendering path**. "Exactly" is meant literally: a `PreviewLayer` carries the unrounded rolled `(H,S)` **alongside** its color spec and draws from the former, because every spec resolves through 8-bit RGB and a rolled hue between two representable colors cannot be spelled — rendering through the string put the preview ~0.25° off the asset. The spec stays for humans to read and re-run.
  - `Generation/` — RNG, weighted roller, color roller, DNA, rules engine, orchestrator.
  - `Output/` — dual per-item metadata (standards-pure OpenSea `metadata/NNNN.json` + rich `nfty/NNNN.json` with dna/seed/rarity/per-layer color) + set writer + extend loader. `set.json` records `cookbookSha256` — the hash of the source `.cbk`, carried on `LoadedCookBook.SourceSha256` (populated by `CookBookArchive.Read`, **null for an in-memory book that never came from a file**) → `GeneratedSet` → `SetManifest`. It is what ties a Set back to the exact archive that produced it, so keep it threaded through.
  - `Stats/` — rarity computation, plus the text reports the CLI prints (`CollectionReport`, `IdentityReport`, `KitchenReport`, and **`VoxelReport`** — which variants carry *partial* alpha, the one thing a voxel converter cannot resolve; partial alpha is legal, so that is a **report and never a `Validator` problem**, and it is opt-in via `inspect --voxel` because it costs a full scan of every variant image). Rendered here so the GUI shows byte-identical text rather than something similar. Reports format **invariant** — they get copied and compared across machines — and degrade to a line rather than throwing when a book's DNA space cannot be counted.
- **`Nfty.Cli`** — thin `System.CommandLine` wiring. Command definitions live in `CommandFactory.cs` (authoring commands in the `CommandFactory.Authoring.cs` partial); `Program.cs` just invokes it. Commands: `inspect` (any of the four archive kinds, including a `.ktn`, which it lists), `validate`, `stats`, `preview`, `generate`, `extend`, plus authoring — `new ingredient|recipe|cookbook|kitchen`, `add variant|ingredient|recipe`, and `move ingredient` (manifest JSON + PNGs, resolved by the `{id}.png`→`{id}.igt`→`{id}.rcp` convention; `Validator.ValidateIngredient`/`ValidateRecipe` gate the per-level builds). `inspect` also prints a book's own **palette** (the swatches an archive carries, so a collection handed on brings its colors with it) and takes **`--voxel`**, refused on a `.ktn` — a Kitchen lists paths without opening them, and an option that silently does nothing is worse than one that says no. `preview` takes **either** an `.igt` (one variant, `--variant`/`--color`) **or** a `.rcp` (the whole stack, `--seed`/`--only`/`--with`), dispatched by `Archives.KindOf`; options belonging to the other form are **rejected**, never ignored. A `.rcp` has no canvas of its own, so the recipe form takes the size `Validator.ValidateRecipe` has already proved every variant shares — deliberately not a `--canvas` flag, which would render a preview at a size no CookBook could cook at.

**Errors surface through `ErrorReport.Format`, not raw traces.** `Program.cs` sets `EnableDefaultExceptionHandler = false` — without it `System.CommandLine` catches first and prints `Unhandled exception:` plus a trace, and `Program`'s own handler never runs. Commands themselves catch nothing: they throw, and `Program` prints the message (plus the trace only under the recursive `--verbose`) and returns 1. Engine exceptions are expected to carry a message worth showing a user verbatim — that is why `ErrorReport` prints `ex.Message` rather than the type name. `Nfty.Cli.Tests` covers `ErrorReport` and that the command surface parses; engine behavior is covered in `Nfty.Core.Tests`, so put real assertions there.

**Callers own image disposal.** `Nfty.Core` returns live `Image<Rgba32>` objects. This covers **both directions**: reading an archive eagerly decodes every variant PNG, so `LoadedCookBook`/`LoadedRecipe`/`LoadedIngredient` are `IDisposable` too and each disposes what it owns down to the variant images — `using var book = CookBookArchive.Read(path)` frees the whole tree, and a GUI that opens and closes cookbooks must do so. On the output side, `GeneratedAsset` and `GeneratedSet` are `IDisposable` (disposing the set disposes every asset image), so `using var set = Generator.Generate(...)` is the default — see `generate`/`extend` in `CommandFactory.cs`. `Generate` materializes the whole collection in memory; a consumer that can't afford that (a GUI grid over 10k assets) should use **`Generator.GenerateStreaming`**, which yields one asset at a time and hands ownership of each to the caller — an abandoned enumeration leaves the last asset undisposed.

### Sync/async pairs

Every I/O entry point has an async twin; `Generate` also takes an optional `IProgress<GenerationProgress>` and `CancellationToken` (`SetWriter.WriteAsync` reports `WriteProgress`). The split is deliberate and worth preserving:

- **Genuinely async** (real awaits on stream/JSON/PNG-codec work): `CookBookArchive`/`RecipeArchive`/`IngredientArchive` `ReadAsync`/`WriteAsync`, `SetWriter.WriteAsync`/`ReadExistingAsync`. Note `ZipArchive`'s own directory parsing has no async API — only the per-entry I/O awaits.
- **CPU-bound, offloaded**: `Generator.GenerateAsync` is a `Task.Run` over the sync core. Rolling/colorizing/compositing has nothing to await; it exists to keep a UI thread free. **Don't add fake `async` to the generation loop** — put new work behind the progress/cancellation parameters instead.

### Color specs

Anywhere a user enters a color it must carry an explicit prefix — `hex:`, `rgb:`, `hsl:`, or `hsv:` (e.g. `hex:d6249f`, `hsv:322,83,84`). A missing/unknown prefix is a **validation error, never guessed** (`Imaging/ColorSpec.cs`). For dynamic/static colorization only `H`/`S` are taken from the color; value/lightness comes from the grayscale value-map.

## Conventions

- **PR-per-task, one fresh agent per major task.** Work lands on a local feature branch merged into `main` — see `docs/superpowers/` for the design spec and implementation plans. **The spec (`docs/superpowers/specs/`) wins over the plan docs (`docs/superpowers/plans/`)**, which are stale — they predate the Custom kind and describe a two-kind `LayerKind`. Where the shipped archives contradict even the spec, the archives win: `schemaVersion: 1` is out in the world, so the doc gets corrected, not the format.
- The **Avalonia GUI** is the second front-end (cross-platform incl. mobile), built on `Nfty.Core`. Keep `Nfty.Core` free of UI/CLI dependencies so both front-ends can share it. **The running app is the source of truth for how the app looks.** The seven HTML screens that preceded it are archived under `docs/design/archive/mockups/` and are history, not specification — the design has been revamped many times since, and nearly every improvement came from building a screen, looking at a rendered frame, and changing it. A difference between the app and an archived file is **not a divergence and needs no justification**; do not open one as a defect, do not comment one as deliberate, and do not "restore parity". The archive is still worth reading for *why* a decision was made — much of the app's vocabulary was settled there (the oxblood accent, the mono/sans pairing, the `idchip` badge shape, the kind colors) and code comments cite those files by name — but a citation explains provenance, never obligation. Do not edit anything in the archive: it is a dated record, and editing it to match today's app destroys the only thing it is still good for. See `docs/design/archive/README.md`.

### GUI: state and house rules

The visual-polish work is merged into `main`. **`docs/superpowers/specs/2026-08-02-gui-visual-polish-status.md` is the running handoff** — which of the 12 audit slices are done, what is deliberately left open, and why. Read it plus `2026-08-01-nfty-gui-visual-audit.md` before touching the GUI.

- **Verify visuals from a rendered frame, never from the markup.** `NFTY_CAPTURE=1 NFTY_CAPTURE_DIR=<dir> dotnet test tests/Nfty.App.Tests --filter FullyQualifiedName~VisualCapture`, then *look at* the PNGs. Page frames render at **1180x720** — the mockups' own units, which is what a page's layout is authored against; the pane track alone needs 1014px, so a smaller capture makes correct layouts look clipped. The **shell** frame is captured at **1416x864** instead, because the whole shell renders at `ShellViewModel.BaseScale` (1.2) and that is MainWindow's real size. Nearly every defect in this branch was found this way and would have been missed by reading code.

  Two companion tests catch what a frame can't. `DarkModeContrastTests` walks every screen in both themes and scores each text run against the surface it actually lands on, compositing alpha through translucent ancestors — it found "1 problem" rendering as opaque Black at 1.14:1, in the invalid-CookBook state no fixture had ever built. `ThemeResourceTests.Every_dynamic_resource_the_markup_references_resolves_in_both_themes` derives its key list from the markup rather than a hand-written list, because that bug's cause was `WarningBrush` being referenced and defined nowhere — **an unresolved `DynamicResource` does not throw; the property silently keeps its default.**
- **The harness must render the shipped control, never a replica.** The shell chrome lives in `Nfty.App/Views/ShellChromeView.axaml` rather than in the desktop head specifically so the capture can reach it — a hand-written mirror had been drifting from the real titlebar with nothing to detect it.
- **US English, everywhere the product speaks.** Colour/grey/centre/behaviour/cancelled and the rest are rewritten as color/gray/center/behavior/canceled — in UI strings, identifiers, comments, CLI output and the docs a user reads. The archived mockups keep their British labels (`Grey`, `Colour`, `True colour`) because nothing in the archive is ever edited — not a divergence, just an old file. `docs/superpowers/` is a dated record and is left as written. Beware one collision the rename actually hit: `UniqueSpace.ColourBuckets` (a method) became the name of the existing `ColorBuckets` class, and is now `CountColorBuckets`.
- **Fluent's horizontal Slider does not centre its own thumb.** It reserves a tick lane below the track, so the handle draws ~5px under the control's middle. Every slider here is laid over or beside something it must line up with (a value ramp, a hue band, an "A" label), so `Slider.overlay` carries a cancelling `Margin="0,-5,0,5"` — the margins sum to zero, leaving the height untouched and the handle on the band. A slider that needs a visible track can't take that class and repeats the margin inline. `EditorStripAlignmentTests` measures it.
- **There are exactly two field sizes, and they are tokens.** `FieldHeight` (32) is a FORM field — a wizard input, a name, a weight, a description. `FieldHeightSm` (26) is a COMPACT NUMERIC CELL in a dense strip or rail — the range end-inputs, the quantize steppers, the brush size. The colorize rail had been neither: 24px range boxes stacked directly above 32px quantize steppers, which reads as two unrelated controls rather than two of the same kind. Both live in `Tokens.axaml` so a new input **picks** a size instead of inventing one, and `Every_compact_numeric_cell_is_the_same_height` reads the token rather than restating the number.
- **Fluent's `TextBox` carries a 64px `MinWidth`, which silently beats a smaller `Width`.** `TextBox.nin` said 58 and every one of them drew at 64 — consistent with each other, so nothing looked wrong, and the markup simply was not describing the frame. Set `MinWidth="0"` *before* any `Width` under 64 on a `TextBox` or a `NumericUpDown`'s inner box. The test asserts `Bounds.Width == Width` rather than a literal, so the invariant is "a declared size is the real size", not "58".
- **A number a user reads while dragging must not change shape.** The colorize range endpoints are `double`s bound straight to their `.nin` boxes, so a slider reporting `137.42786885245902` put that in the field: the box changed width mid-drag and a spinner press turned a bare `0` into `0.5`. Two halves to the fix — the overlay sliders carry `TickFrequency="1" IsSnapToTickEnabled="True"`, and the four `On*Changed` handlers round and re-assign (idempotent, so the generated setter drops the equal value and it settles in one hop). It is an **authoring** narrowing and nothing more: `ColorRange` still carries doubles, the CLI can still write a fractional endpoint, and no generation arithmetic changes. Every `NumericUpDown` also states a `FormatString` (`0` for the integer ones, `0.##` for weight) for the same reason.
- **A preview that takes over the pane must leave its own way back.** The editor's corner tile hid itself whenever "fill pane" was on — and it carries the three buttons, so the only control that could turn fill-pane *off* went with it and the way out was to leave the screen. The tile is always present now and the two images simply **swap**: the small tile shows whichever of the pair the big canvas is not, so its caption (`PREVIEW`/`SOURCE`) always names something on screen exactly once. Its size is **bound**, not fixed — "enlarge" moved a `PreviewHeight` the markup had hard-coded past, so the middle button did nothing at all, and no ViewModel test could see it because the ViewModel was right. The three sizes are monotonic (tile, tile enlarged, whole pane), so enlarged stops short of the 320px canvas rather than duplicating the button beside it.
- **A height pinned on a `NumericUpDown` clips the box that draws.** The border belongs to the `TextBox` inside the template, which keeps its own 32px floor; setting only the outer control's `Height` cut the box's top and bottom edges off while still reporting the height you asked for. Put the height on the inner `TextBox` (`NumericUpDown.nin /template/ TextBox`) — one hop, which is allowed — and leave the outer control to measure whatever it likes, since nothing paints there.
- **Token brushes only in Views.** No raw hex outside `Themes/Tokens.axaml`; a new color goes in **both** dictionaries. Avalonia hex is `#AARRGGBB` — the mockup CSS is `#RRGGBBAA`, so alpha moves to the front. **A gradient must be a whole brush per theme dictionary**, never a `LinearGradientBrush`/`RadialGradientBrush` built inside a `Style` `Setter` with `DynamicResource` stops: that brush is constructed once and shared, so its stops never re-resolve on a theme change. It shipped the CookBook identity card painting its light gradient in dark mode, and is invisible in light mode, in the markup, and to any single-theme test. `ThemedGradientTests` guards it.
- **Geometry is fixed: reserve the space, toggle the ink.** A control appearing or disappearing must not move, resize or reflow anything around it — a table is the same width locked and unlocked, a row the same height active and inactive, at every window size. Use `Opacity`/`IsHitTestVisible`, **never** `IsVisible`, on anything that occupies layout, and fixed column definitions rather than `Auto` where the content can vanish. Prove it by pixel-diffing two captured frames, not by eye. The knowing exception on record: the always-present grip column gives the locked Layers table a 26px gutter `explorer.html` does not draw, accepted because the locked set has no reorder affordance at all.
- **A pointer-drag gesture is pointer capture, not `DragDrop.DoDragDropAsync`.** The latter needs a platform drag *source* and `Avalonia.Headless` registers none — `IPlatformDragSource` is absent from the assembly, and a call under the harness never returns. It would also make the gesture uncapturable and untestable, against the rule above it. And **drag always ships with a keyboard path** (`Alt+Up`/`Alt+Down` over `LayerDepth.MoveBy`); pointer-only reorder is an incomplete feature, not a scoped-down one. Note `ObservableCollection.Move` makes `ItemsControl` **drop and recreate** the moved container, so focus must be restored at `DispatcherPriority.Loaded`, behind the layout pass — without it the second keystroke is silently swallowed.
- **Avalonia is 12.1.1**, on .NET 10. `Grid.ColumnSpacing`/`RowSpacing` and control-level `LetterSpacing` exist — use them rather than per-child margins or a TextBlock-inside-Button. All three test projects run on **xunit.v3**; `Avalonia.Diagnostics` is now `AvaloniaUI.DiagnosticsSupport`, and the text shaper is opt-in via `Avalonia.HarfBuzz`.

Never set `Width`/`Height` on a `Path.ico` inline — use the `xs`/`sm`/`ti`/`lg` classes, which carry the matching transform.
- **`assets/icons/*.svg` are the drawings; `Icons.axaml` is generated from them** by `python tools/icons/build.py`. Edit the SVG, run that, commit both. `IconSourceTests` fails the build if the two disagree in either direction, which is the whole point: without it the obvious repair for a wonky glyph is to nudge the path in the axaml — it is the file the app reads, the edit works, and the SVG quietly stops being the drawing while still looking like it is. That is how every unchecked "source of truth" dies. Avalonia cannot render SVG without a library, and adding one to draw 45 static glyphs is a poor trade, so the generated copy stays committed. `assets/icons/README.md` carries the rules a glyph follows.
- **The demo CookBook is a shipped feature, and `src/Nfty.Core/Demo/ChestDemo.cbk` is a generated file that is committed.** `tools/demo/draw-chest-art.py` draws the sprites and `tools/demo/build-demo.py` drives the CLI's own authoring commands to assemble the archive — the same arrangement `Icons.axaml` has with `assets/icons`, for the same reason: the generator is the source, but the build must not need Python. Edit the generator, re-run it, commit the `.cbk`. **Do not edit the archive by hand and do not re-run the build casually**: a `.cbk` is a ZIP and its entry timestamps change on every write, so a rebuild produces a different binary from identical content, which is a diff nobody can review. `DemoCookBookTests` reads the EMBEDDED bytes and validates, counts and cooks them; the file and the script cannot drift in silence. Three rules the demo has to keep, each pinned by a test. It is **embedded, not installed beside the executable** — two of the four published shapes are a single `.exe`, so a file next to the binary is absent from exactly the copies most likely to travel. Its **quantize steps are chosen so `UniqueSpace` counts it exactly** rather than saturating the million cap, because a demo whose headline figure is "more than 1000000" teaches the reader that nfty cannot count its own space. And **`DemoCookBook.WriteTo` does not overwrite by default** — the demo exists to be edited, and a second "open the demo" that restored the shipped bytes would silently throw away the user's work. The art itself obeys a fourth: every overlay (bands, lock, trim) is authored at `y >= 12`, where both lids are the same rectangle, so a strap cannot float in the air on one recipe and not the other.
- **There is ONE icon set, not one per theme.** The glyphs are stroked with `currentColor` and the theme supplies the ink, so the same geometry serves light and dark and there is no second set to keep in step. A remaster improves both at once.
- **A glyph has to differ from its NEIGHBOUR, not merely be correct.** Four were redrawn on that ground, each found by rendering the whole set at 12/14/18px and looking: `select` was a rounded square sitting beside the `rect` tool's rounded rectangle, so one toolstrip had two shape tools drawing the same picture — it is a dashed marquee now, which is also literally what the canvas overlay draws; `import` was an arrow falling into a tray beside `download`'s arrow falling into a tray, so it became an arrow *entering* a container, deliberately the inverse; `kitchen` was a box with a header bar and two hanging tabs, which is a **calendar**, for a thing CLAUDE.md defines as a vault of loose parts — it is an archive box; and `fill` was a bare diamond that read as a rhombus beside the eraser's slanted block, because a bucket is illegible without its handle. The eraser was left alone: once the bucket had a handle the pair separated on its own, and redrawing a working glyph is churn.
- **Fluent fights back, and the fights are documented where they happen.** Style ordering is last-one-wins at equal specificity, so a narrower opt-out must be declared *after* the blanket rule. A selector may cross only **one** `/template/` boundary — reaching a nested control's internals needs its own `ControlTheme`. Neutralising a Fluent state means setting it **explicitly** (e.g. `Transparent`); simply not painting hands the state back to Fluent's stock blue. Some geometry (the slider track; the spinner column, until its template was hand-authored) is fixed inside Fluent's templates at a priority a `Style` setter cannot beat — where that happens the setters were **removed** and the gap commented, rather than left in place looking effective. The same applies to a rule that has *become* dead: two app-wide `RepeatButton` presenter rules existed only to reach inside Fluent's `ButtonSpinner`, and once that template was ours they matched nothing they were written for while still matching every other `RepeatButton` in the app. Removing them changed **zero pixels** across the whole capture set, which is how you prove a rule is dead. And a `ControlTheme` may not contain a **descendant** selector at all (`^:pointerover Path.ico`) — it throws at load, not at build; a top-level `Style` may.
- **Pixel art scales with nearest neighbour, never a filter.** Every image the app shows is generated pixel art displayed at a size unrelated to its pixel count, so each view root that hosts an `<Image` sets `RenderOptions.BitmapInterpolationMode="None"`. It cannot be a `Style` `Setter`: Avalonia 12's `RenderOptions` is a Get/Set pair, not an `AvaloniaProperty`. `PixelPerfectRenderingTests` derives its view list from the markup and reads the **effective** mode off live controls, because the value is composited at draw time and a child reads `Unspecified`. Nothing in `Nfty.Core` resamples, blurs or anti-aliases either — commands write whole pixels and import refuses a wrong-sized image rather than scaling it. Partial alpha is unrelated: a value the author opts into, not a filter.
- **Landing's Kitchen shelf is always present and always one height** — a Kitchen open, none open, or an empty one. That is not polish: it is what lets the workspace live on Landing without opening one reflowing the screen, and it is the argument that a Kitchen is something the app carries rather than something a CookBook has. The three states share **one grid row**, so they agree by construction rather than by three declarations matching — an explicit `Height` on the band was removed because it was a second statement of a number the fixed rows already made, and the two had drifted by a pixel. The band carries **no buttons of its own**: Open Kitchen… and New Kitchen… are already a few inches left of it, and two controls for one action is worse than one. See `docs/superpowers/specs/2026-08-12-kitchen-shelf.md`.
- **Three chrome measurements were sized by eye against a rendered frame, not by arithmetic.** The whole shell renders at `ShellViewModel.BaseScale` (1.2), so anything authored 1:1 arrives 20% heavier. The titlebar is **40** and the Explorer toolbar's vertical padding is **7**, both user-directed after looking at the real window. The third is the editor toolstrip's value ramp at **80**, which is *paid for*: that strip carries a Line tool and a brush-size field, and at the pane's minimum width something had to give — a brightness slider is the one control there whose meaning does not depend on its length. Recorded because each is a considered number that looks arbitrary next to its neighbours, not because it differs from anything.
- **Click-to-sort is one shared class, one rule, and a judgement about which tables get it.** `ViewModels/TableSort.cs`: **the first click on a column sorts ascending, and clicking the active column reverses it** — no descending-first special case for numeric columns, because a table whose direction depends on the type of the column you clicked is two rules to learn. Strings compare **ordinally** (these tables are screenshotted into the manual, and a culture-aware compare lists them differently on a different machine), `OrderBy` is stable so equal keys keep their input order, and an unknown column key falls back to the natural order rather than throwing — which is also how the rules panel expresses "as authored". The notification callback is a **constructor argument**, not something an owner remembers to wire: without it the list property still re-evaluates whenever anything reads it, so every ViewModel test passes and only the running app fails to repaint. **Which tables sort is not a default**: a table's row order either belongs to the DATA or to the READER. The Recipe's **layer table is the standing exemption** — its order *is* `layerOrder`, the paint order, and `Generator.RollOne` walks it consuming one RNG draw per layer, so a sorted view would show a stack that is not the stack, beside a drag handle that writes the real one. That exemption is commented in the view; it is a decision, not an omission.
- **A sort arrow is reserved, and both arrows share ONE slot.** Laid out side by side the pair costs 26px, which the variant table's 56px WEIGHT column did not have — so they were arranged past the column's edge and silently not drawn, exactly as the width-is-a-budget rule warns. They overlap in an 11px `Panel.sortslot` instead, present in every state, so a header's geometry is identical active, inactive and reversed. And on a **right-aligned numeric header the slot LEADS**: trailing, it takes the right edge and pushes the label left, so the header stops sitting over the values it names — which is the defect that table's fixed pixel columns exist to prevent. `TableSortTests` measures both off a frame.
- **The rules panel opens in the order the manifest stores, and that is a contract with the CLI.** `remove rule --at` addresses a rule by its 1-based position and `inspect` is where a user reads that number, so a panel that opened sorted would quietly disagree about which rule is number 3. Sorting is a view the reader asks for; "as authored" is not a column any header offers, it is `TableSort`'s unknown-key fallback. Rule order is otherwise meaningless — `RulesEngine.IsLegal` evaluates every rule — which is exactly what makes sorting safe here and unsafe on the layer table.
- **A filter narrows the view, never the count.** The rules rail's ALL / NEVER / ALWAYS chips filter the rows, but the header badge and the hero's "4 rules" describe the **recipe**; a filtered panel that also changed the count would state the recipe has fewer rules than it has. And the empty state says *which* emptiness it is — "No incompatibility rules" versus "No rules of that kind" — because one of the two is undone by a click and the other is not.
- **A form that creates something opens in a state that can be SAVED.** The rule dialog opened already refused, twice, and both were caught on a rendered frame rather than by a test: `+ Target` seated each new row on the first layer in the list, so a second target was an exact duplicate of the first; and the Add form seated its trigger and its target INDEPENDENTLY, each on a value nothing else used — and the PAIR they formed was the recipe's existing first rule, because a first rule is usually made of first things. Seating halves separately is the trap: legality is a property of the whole, so search for the first legal WHOLE and seat both from it. Neither refusal was the user's doing, and a form that greets you with a warning teaches you to ignore warnings.
- **`DarkModeContrastTests`' screen list is hand-written, unlike the markup-derived sweeps.** `PixelPerfectRenderingTests`, `WiringCoverageTests` and `ThemeResourceTests` all enumerate the views themselves, so a new view joins them for free — the contrast sweep does not, and a screen it never walks cannot be found unreadable. A new view is added to `Screens()` **in the state that carries its riskiest ink**: the rule form is seated on a rule it cannot save, so the sweep meets its `WarningBrush` sentence and its disabled accent button rather than the clean state. Probed by recolouring that sentence — both themes then fail, at 1.29 and 1.40 against a floor of 2.0.
- **A record with an `IReadOnlyList` member does not compare structurally.** `IncompatibilityRule.Targets` is one, so two rules that mean the same thing are unequal whenever the lists are different instances — which every JSON round-trip guarantees (an array in, a `List` out). `RuleEdits.AreSame` is the comparison to use; it also treats the targets as a SET, since a rule's targets are a conjunction and listing them in another order is the same rule written twice.
- **A `Border` with no `Background` is not hit-testable.** In Avalonia `null` means *nothing here*, not *nothing painted* — so a row that sets a border, a padding and no background never enters `:pointerover`, and anything revealed on hover inside it is unreachable by mouse. The rules panel shipped that way: Edit and Delete were laid out, reserved, tested for their reserved column and their two buttons, and could not be reached at all. **No rendered frame could show it and no layout assertion could catch it, because the geometry was always right** — it took driving the running app. Set `Background="Transparent"` on any row that reveals something on hover, and assert it with a HIT TEST (`GetVisualAt` from the row's own centre) rather than by checking the property, since the property is the mechanism and reaching the row is the requirement.
- **A filtered view must not narrow anything that describes the whole.** The rules panel's count badge was bound to `HasRules` — the FILTERED list — so a filter matching nothing hid the badge and told the reader a recipe with two rules had none. Counts, badges and hero sentences bind to the recipe (`RecipeHasRules`); only the rows and the empty state bind to the view. Note `!HasRules` is true in **both** empty cases, so the filtered-empty message needs its own `FilterEmptied` (`RecipeHasRules && !HasRules`) or it draws in two grid rows at once on a recipe with no rules.
- **A layer can be left out entirely, and the chance lives on the RECIPE.** `RecipeManifest.AbsentPercent`, keyed by ingredient id — the `CookBookManifest.RecipeWeights` shape one level up, additive and optional so `Schema.Current` is **not** bumped. It could not live on the ingredient: an `.igt` is a standalone file a Kitchen hands to any project, so the same Hat is guaranteed in one recipe and a chase item in another. A **percent**, not a probability (0..1 means a conversion at every boundary a human touches; a percent converts once, in the roller) and a **chance**, not an absent weight (store a weight, then double every variant weight, and the layer silently gets commoner). 100 means shelved, exactly as a recipe weight of 0 already does.
- **The absent outcome is drawn AHEAD of the weight table, never added to it, and that is the whole design.** The key array and its ordinal order are untouched; `total` is `0 + table.Total`; `r < 0` is false and `r -= 0` changes nothing. So a cookbook that does not use the feature rolls **byte-identically** from the same seed and every Set ever generated stays reproducible. Pinned by rolling 2,000 draws through both overloads from one seed and comparing key for key — not statistically — and probed by making the overload consume one extra draw.
- **An absent layer contributes no DNA part and no colour.** No sentinel marker: a marker would have to be a string no variant id could ever equal, and omitting is unambiguous without one because a present layer adds a part an absent one does not. Rolling no colour is what stops two assets that both show nothing on a Dynamic layer from having *different* DNA — the exact trap that makes a transparent-variant workaround unsafe on anything but a Custom layer.
- **`combos × buckets` stopped factorizing.** `UniqueSpace` multiplied legal combinations by the product of every dynamic layer's colour buckets, which was only valid because every legal selection had every layer present and therefore carried the same product. An optional layer contributes **one** shape absent and `variants × buckets` present, so the space is a product of per-layer shape counts with no rules and a **sum of per-selection products** with them. The count is a promise, so its tests generate the whole space and count what comes out rather than checking the formula.
- **A view that shows a share must fold absence into it.** `RarityCalculator` computed each variant's share among its siblings, so the moment a layer became optional a one-in-twenty chase item printed "50% in recipe". Every surface reading those numbers — the ingredient table, its mini bars, the reports — was wrong at once. And the Ingredient pane resolves its absent flag from the **book's** copy of the recipe, because that is where `RarityCalculator` gets the percentages: read them from different objects and the flag can say 90% above variants still showing their sibling share, which is what a capture fixture did.
- **A share bar must be a fraction of the track it is actually in.** Three of the four in this app pin their track (`.distbar` 310, `.rt` 120, `.mixbar` 270) and a constant multiplier is exact for them. `.cbar` does not — it is a star column — and `share * 3.1` drew a 100%-of-mints recipe at about four fifths. `ShareWidthConverter` multi-binds the track's own `Bounds.Width` instead. A new bar in a flexible track uses that one.
- **A slider laid over a band lives in a `Panel.band`, pinned to 40px.** Fluent puts a Slider's thumb **center 25px below the control's own top**, whatever height the Slider is given, and `Slider.overlay` lifts the control by 5 to cancel that — which is exact for a 40px row and wrong for every other. The dual-range rows measured 50, so all four handles sat 5px above the bar they dragged along: the compensation was the fix for one row height and the bug for the other. Pinning the row makes it true by construction, and `Every_handle_is_centered_on_the_band_it_drags_along` asserts **band center == thumb center** across the editor *and* the wizard rather than any one number — the previous test checked a single band and passed the whole time. The handle fills with `OnAccentBrush` (the token for ink on a saturated ground), not `PanelBrush`, which is near-black in dark mode and made it read as a hole punched through the bar.
- **A button's size is a class property, and a class that omits one inherits Fluent's.** `Button.accent` set no `FontSize`, so it took Fluent's 14 while every `Button.tbtn` beside it was 12.5 — "Add recipe" came out 37px tall against Delete and Import at 35, in one row, where two pixels read as a mistake. Both classes now also center their content; `tbtn` was `Left`, which is invisible while a button hugs its label and wrong the moment one stretches. `ToolbarButtonParityTests` pins both.
- **Tooltips are a themed control with a 2.2s delay, not Fluent's default.** The app had no `ToolTip` theme at all, so every tip — the kind chips, the DNA derivation, the wizard help badges, every icon button — drew a stock gray slab in a system font, on the one surface that never spoke the palette. The theme is panel ground, `LineStrong` hairline, `RadiusSm`, the app's 11.5px, a `MaxWidth` so a sentence wraps, and a 140ms fade; no `BoxShadow`, because a popup surface sizes to its content and would clip it. The **delay** is what stops the bombardment: at Avalonia's 400ms, crossing a toolbar pops a tip on every button on the way. It is set once, app-wide, by `Style Selector=":is(Control)"` — the bare `Control` selector matches the exact type and so would apply to nothing. The single exception is `Border.qmark` at 600ms, the one control whose entire purpose is to be hovered.
- **The Ingredient editor's rail is two tabs, `COLORIZE` and `REFERENCES`.** Together they overflowed the rail and the half that lost was the references — the sibling list and the Kitchen section sat below the fold with nothing on screen saying they were there. They are also two different jobs: one sets what the layer looks like, the other what you are looking at it against. The tabs sit in the pane's own 41px header, so the split costs no height; underline rather than a segmented tray, because a tray would land directly above the Dynamic/Static tray and two stacked pills read as one control with four options. Each tab carries its 2px underline in **both** states — transparent when off — so switching moves nothing (`RailTabTests`). The count badge is `RadiusXs`, not a pill: a pill radius in this app means *track*.
- **"Reserve the space, toggle the ink" has one recorded exception, and it is positional.** The reference panel's stack-mismatch banner followed the rule and paid a permanent 34px hole in the middle of the panel — visible in every ordinary session, where there is no problem at all, and reading as a layout mistake. It is the **last** thing in the panel now and simply uses `IsVisible`: the rule exists to stop a control appearing under the pointer that just acted and shoving rows away, and nothing sits below it to be shoved. Moving a toggled control to the end of its container is the way out of the rule; a bare `IsVisible` in the middle of one is not.
- **The second exception is a REVEAL, and a reveal is allowed to reflow.** The Recipe layer table's ABSENT column is not there until the OPTIONAL LAYERS chip asks for it, and turning it on moves KIND and VARIANTS left. That is not the bug the rule is about: nothing appears under the pointer that just acted, the affected columns are read-only text, and the alternative is a permanent 96px gutter in every recipe that will never use the feature — the same argument the reference banner won on. What the rule still buys is that the column's **header and its rows collapse together**: both cells are one styled wrapper (`Panel.chancecell`, one width stated once in `Styles.axaml`), so the `Auto` column measures 0 in *both* Grids and cannot half-appear. That is the only reason an `Auto` column is admissible in a two-Grid table here at all; see the header-Grid rule above for what happens otherwise. Avalonia offers no bindable `ColumnDefinitions`, so a collapsing `Auto` is the mechanism, not a shortcut.
- **Avalonia has no baseline alignment, and the default is worse than either choice.** The idea came from the archived screens, which say `align-items: baseline` in five places (`.rchip`, `.rules-h`, `.cwaxis`, help's `.cs`, the editor's `.ctl-h`). A `TextBlock` in a horizontal `StackPanel` defaults to `Stretch`, which draws its line at the **top** of the row — so a 9.5px caption beside a 12.5px name missed by **4.7px** and the rule chips read as broken; `Center` is no better across two sizes, it only moves where the error lands. `VerticalAlignment="Bottom"` flushes the boxes and leaves only the descent difference (~0.7px). About **1px is irreducible**: this app pairs a mono face with a sans one in every data table and the two have different descents; a shared `LineHeight` was measured and bought 0.1px, which is not worth a size stated twice. `TextBaselineTests` sweeps every screen, finds rows from a **laid-out frame** (anything whose vertical extents overlap, so a Grid cell counts too — which is how it caught the ingredient card's kind line), and fails above 1.25px.
- **`MaxWidth` on a `Stretch` control centers what it caps.** CSS `max-width` on a block element keeps it at the left edge; Avalonia centers it in the slack. The CookBook's own description floated 205px in, under nothing, while the title above and the chips below both started at the card's edge. `ExplorerView`'s tree column carries a note about the same trap — assume any `MaxWidth` without an explicit `HorizontalAlignment` is centered, and check it on a frame.
- **A header Grid and a row Grid are two Grids, and `Auto` sizes them independently.** The ingredient's variant table put "WEIGHT" over a column sized by the header word and its numbers over one sized by the widest number, so the values sat 10px right of the label naming them and moved whenever a weight gained a digit. Fixed pixel columns in **both**, as the recipe's layer table (`26,40,*,110,90`) already does. There is no `SharedSizeGroup` in Avalonia. **It happened again**, in the Set browser's rarity table, and the second sighting is the instructive one: its VALUE column was `Auto` in both Grids, the header measured "VALUE" and the rows measured "Cat", and the label had stood ~18px left of the values it named since the table shipped. Nobody saw it until a sort arrow widened the header enough to make the gap obvious — an `Auto` column in a two-Grid table is a latent misalignment, not a working one that later broke.
- **Fluent paints a disabled `RepeatButton`'s wash on the presenter inside it.** Setting `Background` on the button changes nothing (verified off a rendered control: button `Transparent`, presenter still `#33ffffff`), the presenter is a second `/template/` hop from the `ButtonSpinner` theme, and a type-keyed `ControlTheme` never applies because `ButtonSpinner`'s template hands its buttons an explicit `Theme`. A **top-level** `Style` reaches it in one hop. The symptom: a spinner arrow at its limit was the one control in the app that got *brighter* when it became unavailable.
- **A figure on screen must come from the code that owns it.** The Ingredient editor printed `HueQuantize * SatQuantize` — the product of two *step sizes*, which counts nothing: it ignored the ranges, read "600 colors" where the layer admits 36, and **rose** when a coarser step made the palette smaller. It now calls **`UniqueSpace.CountColors`**, the same counter the DNA space multiplies per dynamic layer, so the editor's figure and the CookBook's cannot disagree. Same class, same panel: the DNA-space row drew `chips = total`, but the total is *legal* combinations (rules subtract) times quantized colors, so the chips' product is neither factor and no extra chip could make the equation true — it is an arrow now, with the derivation on the tooltip. And those chips follow **`layerOrder`**, not `recipe.Ingredients`, so the same five numbers are not shuffled between two panels one click apart.
- **A command nothing references is a button that does nothing.** Landing's "+ Recipe" was `ShowAsync<object>(new NewRecipeViewModel(...))` — the wizard collected a name, a weight and a destination and the result was dropped on the floor — while "+ Ingredient" beside it, which looks identical, was fully wired. No test named `NewRecipeCommand`, so nothing failed. Found by driving. `WiringCoverageTests` checks that markup bindings resolve; it cannot tell whether a command's body does its job, so a command with a body worth having gets a test (`LandingNewRecipeTests`).
- **`DeadCodeAuditTests` closes the three holes a binding sweep cannot see, and every one of them has shipped here.** `WiringCoverageTests` asks whether each declared command is reachable; these ask the questions on either side of it. **A Button with no `Command`, no `Click` and no bubbled `Button.ClickEvent` in its own code-behind** — the third is a real pattern, not a loophole: the Set browser's tiles read the row's DataContext from one handler rather than hopping two DataContexts up a template. **A `[RelayCommand]` with an empty body** — the Ingredient hero's old "Jump to rules" was a visible control, a binding that resolved, a command that existed and a method with nothing in it, and every test passed; a body that is only a comment counts as empty, because a comment does not run. **A style class, icon or token defined and never used** — dead decoration is not merely clutter, it is what gets copied onto the next control, and 258 classes is past what anyone keeps straight by hand. The token sweep is the mirror of `ThemeResourceTests`, which walks the other way; it carries an exemption for `TextControlPlaceholderForeground`, which **Fluent's** template reads and this repo therefore never names. Both exemption lists assert they are not stale, like `WiringCoverageTests.Exempt`.
- **Prove a deletion is dead by pixel-diffing the whole capture set, not by reading the code.** The `RepeatButton` rules set that precedent; the phase-6 sweep followed it, and `IngredientEditorViewModel.PaletteSlots`, `ArchiveIo.ReadImage`/`ReadImageAsync` and three `Color` tokens came out against **68 frames byte-identical**. The two `ArchiveIo` helpers are the instructive ones: they were the pre-split combined form, still compiling and still correct, and reaching for `ReadImage` would silently take the sequential decode that the extract/decode split exists to avoid. The three `Color`s were worse than unused — the gradients that were supposed to consume them spell their stops as literals (a whole brush per dictionary, per the rule above), so each number was stated twice per theme with nothing keeping the two in step.
- **A JOURNEY test is the repeatable version of driving the app.** Driving is what found the wizard result dropped on the floor and the rules row nothing could click, and it is not repeatable. `OptionalLayerJourneyTests` is the shape to copy for a feature that crosses layers: start at the ViewModel the view actually binds to (`CommitAbsentAsync`, which is what lost-focus calls), go through the real Explorer seam and its edit lock, land in a real `.cbk` in a temp directory, **reopen that file** and cook it, then assert on the assets. The last step is the one the ViewModel tests cannot make: a chance that reached the manifest and changed no pixel passes all of them. Probe it by breaking the far end — zeroing the roller's absent branch fails only the cooking test, and no-opping `AbsentChance.Set` fails four of five.
- **A routed event's Source is the control that has focus, which is inside the template.** The chance field's lost-focus handler tested `e.Source is NumericUpDown { Name: "AbsentField" }`, and focus never rests on the NumericUpDown — it goes to `PART_TextBox`. That match succeeded exactly once, on the LostFocus the outer control raises while handing focus *inward*, which fires as the user ARRIVES and carries a value they have not typed yet; the departure, sourced at the TextBox, was ignored. **Tabbing out of the box silently discarded the number.** Walk UP from the source (`FindAncestorOfType<T>(includeSelf: true)`) rather than testing it — which the reorder grip's own `GripUnder` already did. Enter was broken by the same root cause with a different mechanism: a `TextBox` marks Enter **handled** before it leaves the control, so a handler registered the ordinary way never runs. It needs `handledEventsToo: true`, and narrowly — on the rows, for Enter alone, because taking handled events on the whole view would hand Escape and Alt+Up/Down to keys a child has already dealt with.
- **A test that calls the command is not a test that the control invokes it.** Every test of the chance field — the pane tests, the journey test — called `CommitAbsentAsync` directly, so both bugs above shipped green. `ChanceFieldGestureTests` names no command at all: it focuses the real control, moves focus or presses Enter **from the inner box, where a real press is sourced**, and asks what was written. `TileClickGestureTests` does the same for the Set browser's bubbled `Button.ClickEvent`, the app's other code-behind wiring — it was equally unexercised, and it clicks the SECOND tile because the browser opens with the first already selected.
- **Two vacuous assertions were caught by probing, and both had the same shape: asserting a value the framework supplies anyway.** `header.Bounds.Width <= cell.Bounds.Width` passes at every size, because a TextBlock is arranged to its parent and clips — measure the ink with `FormattedText` instead. And `Assert.True(e.Handled)` after an Enter press passed while nothing of ours ran, because the TextBox sets it — assert the observable consequence (a commit happened, the table did not reorder) instead. If an assertion cannot be made to fail by breaking the code it names, it is decoration.
- **Width is a budget, and an overrun is silent.** A `Grid` star column whose siblings outgrow the pane is arranged at **zero width** — no exception, no warning, the content simply is not there (it shipped that way in the palette strip's first cut, with a correct ViewModel behind it). A horizontal `StackPanel` in a clipping `Border` fails the same way from the right-hand end: adding the Line tool cost 36px the editor toolstrip did not have and pushed the brush-size field off the pane, which only the rendered frame showed. A clipped control still reports its own non-zero `Bounds`, so assert **containment** inside the parent, not `Bounds.Width > 0` — and against the parent's *content* box, since a control that clears the border but not the padding is already touching the edge. `PaletteStripLayoutTests` and `ToolstripLayoutTests` are the pattern; both also assert a slack margin, because fitting exactly is one style tweak from not fitting. **A size stated twice will drift**: `Border.ramp` carries no `Width` so the strip's budget lives only in the view.
- **A shape tool without a rubber band is drawn blind, and a marquee is not a selection.** Both were affordances with nothing behind them. The overlay (`CanvasOverlay`, a hit-test-invisible `Canvas` over `CanvasImage`) draws the in-progress outline and the standing marquee in control coordinates, mapping through the same `Stretch="Uniform"` letterbox `AddPoint` uses — get that wrong and every ViewModel test still passes, so `EditorOverlayTests` asserts it off a laid-out frame. **Select is two gestures told apart by where the drag starts** (outside marks, inside moves) — no modifier, no second button — and marking changes no pixel, so it is not an undo step. **Which gesture it is must be decided at PRESS, not at release**: the ViewModel resolves it on release, so the view asks `SelectionContains` up front and drags the marquee itself during a move. Without that the overlay drew a growing *new* mark box mid-move — the opposite of what release was about to do — and only driving the real app found it. A **Line needs no new Core command**: `RegionEditCommand.StampDiscs` joins consecutive path points with Bresenham, so a `BrushStroke` of just `points[0]` and `points[^1]` *is* a straight line at the brush's size.
- **A `$parent[…]` binding from inside a `ContextMenu` never resolves** — a ContextMenu is not in the visual tree — and fails silently, taking the whole item template with it. Hand the item its own command instead (`PaletteSwatch.ForgetCommand`), and exempt it in `WiringCoverageTests` with the reason.
- **The app dims disabled controls to 0.38 opacity**, which is legible over a full-strength foreground and *not* over an already-muted one (`DarkModeContrastTests` floor is 2.0). Don't disable muted text; swap the ink inside a fixed-size cell instead.
- **The status bar is a last-message board, and a message belongs to the page that said it.** `ShellViewModel.OnCurrentPageChanged` clears it, then lets the arriving page say its own opening line — the Explorer's is its lock state, which the titlebar chip shows at the same moment and must never contradict. Two bugs came from not doing this: the Set browser, which has no lock at all, greeted the user with "Editing locked - unlock to make changes.", and the Ingredient Editor opened under the same sentence over a canvas that painted perfectly well. Note the ordering trap — `ExplorerViewModel` announces the lock from its **constructor**, which runs *before* the `_nav.To` that shows the page, so anything said before a navigation is wiped by it. Say it after.
- **The edit lock governs structure, not pixels.** Add, delete and reorder are gated by it; the pencil (`EditIngredientCommand`, no `CanExecute`) deliberately is not, because the editor is also how you look at a layer. That is why the fix above was to the *message*, not the behavior.
- **A label that only appears when a field is empty is not a label.** The Cook dialog's seed box was named by `PlaceholderText` alone and the ViewModel pre-fills a random seed, so the one thing naming the field showed exactly when the field never was empty — the user met an unexplained box of hex. Every ViewModel test passed; the seed round-tripped fine. `CookDialogLabelTests` asserts a real `TextBlock`, and asserts the seed is non-empty first so it cannot pass on an empty dialog.
- **The `ButtonSpinner` template is ours, and that is what makes a numeric field a numeric field.** Fluent's own draws two side-by-side buttons ~32px apiece, so at `Width="94"` the quantize steppers had ~8px of text room and drew "30" as "3" plus a sliver — clipped, with the control still reporting the width it was asked for. Both the button width and the panel that stacks them are fixed inside Fluent's template at a priority a `Style` setter does not beat (Width setters were tried against a rendered frame and changed nothing), so the fix that shipped first was to trim the inner box's padding — treating the symptom, since the chevrons still took two thirds of every field. `Controls.axaml` now hand-authors the whole `ButtonSpinner` template: the mockups' `.stepr`, one `StepperWidth` (17) column of two chevrons on the trailing edge, with `PART_IncreaseButton` / `PART_DecreaseButton` keeping the names `ButtonSpinner.OnApplyTemplate` looks up — it hooks their Click and drives their `IsEnabled` from `ValidSpinDirections` itself, so limit behavior is template-independent. `ButtonSpinnerLocation="Left"` is deliberately unsupported. The chevron buttons carry their own two-element template rather than neutralizing Fluent's `RepeatButton` state by state — shorter than the list of things to switch off, and it leaves no state that can hand itself back. `SpinnerChevronTests` asserts the column as a **ratio** of the field, and asserts the disabled half is dimmer than the working one as a **relation** — the old bug was a direction, not a value.
- **A Kitchen is a vault, not a workspace.** It holds the **loose parts** — Ingredients and Recipes that belong to no one CookBook — so they can be pulled into any project. "A folder you work out of" describes where it sits; the copy has to say what it holds, or a reader learns the wrong thing about what it is for. The quick-reference sheet puts it below a **dashed** rule for the same reason: it is the sixth word, but it is not a link in the `CookBook › Recipe › Ingredient › Variant` chain, and listing it in the run teaches the wrong shape.
- **Key hints come from `Services/KeyHints.cs`, never a literal glyph.** The archived screens draw `⌘` because they were authored on a Mac; this app ships on Windows and Linux, where that names a key the user does not have. One source also stops Landing and the help sheet disagreeing about the same chord.
- **A 1px `Rectangle` cannot draw a dashed line.** It strokes *both* long edges, one left-to-right and one right-to-left, so their gaps land in each other's dashes and it renders solid — correct in the markup, wrong in the frame. Clip a 3px rectangle to 1px instead (`Border.sh-split`), so only its top edge is inside the clip.
- **A `Bitmap` getter must be idempotent.** `SetInspectViewModel.Image` disposed and re-decoded on every read, which looked harmless and killed the running app: Avalonia reads `Image.Source` during **measure**, so the getter disposed the bitmap it had just handed out and the next layout pass threw `ObjectDisposedException` inside `Image.MeasureOverride`. Cache per index; free only when the index moves. No ViewModel test can see this — `SetInspectTests.The_inspector_view_loads_and_lays_out` renders the control, which is the only thing that catches it.
- **`Slider.overlay` blanks the track on purpose.** Every slider in this app except one is laid *over* a band it must not hide, so the class paints `Background`/`Foreground` transparent. The inspector's zoom slider is the one with a track of its own; it takes `Slider.ins-z` and repeats the cancelling `Margin="0,-5,0,5"` inline. Given `.overlay`, it rendered as a lone ring floating between two buttons.
- **The Set browser's selected tile is its ground plus its accent caption — no border.** At 76px any added edge reads as a frame around the art rather than a marker on it. Hover is a **row and a cell**: `Border.trow:pointerover` washes the run, `Button.tcell:pointerover` washes the one under the pointer, which together read as a crosshair. Both are background-only, because anything that changes a size reflows the grid under the pointer.
- **The rarity bar fades.** A flat block does not read as a bar — it reads as a selected row, which is exactly how the first cut looked. `RarityBarBrush` is a whole gradient per theme dictionary (the `CardGradientBrush` rule), and its width multi-binds the row's own measured width through `ShareWidthConverter`, never a constant multiplier.
- **The DNA splits at half, computed.** A SHA-256 is 64 hex characters, so two rows of 32 are always the same width — which is what lets them be centered and line up on both edges instead of only the left. `SelectedDnaTop`/`Bottom` divide by length rather than hard-coding 32, so a hash of another length still round-trips instead of losing its tail.
- **The window minimum is set by the largest MODAL, not by the pages** (`ShellViewModel.MinWindowWidth/Height`, 1128x924). A page can scroll or reflow; a modal is a fixed card that either fits or is cut off, and a quick-reference sheet with its footer sliced away is worse than no sheet. `ModalFitTests` *derives* the requirement from the real controls — measured, the sheet needs 1008x886 and the inspector 1104x838 — so a modal that grows fails with the number it now needs. It follows that **the documentation capture standard is 1416x950**: 864 is a height the app will no longer open at.
- **`ClipToBounds` clips to the layout RECTANGLE, not the corner radius.** A footer band with its own background paints a square corner over the card's arc, and the border reads as cut off at both bottom corners — invisible in markup, where the card plainly has a radius. Every modal's footer (`.sh-f`, `.ins-f`, `.rail-foot`) carries the matching bottom radius itself.
- **Escape closes the modal from the WINDOW, not from the dialog.** The dialog layer hosts its content in a `ContentControl` that never takes focus, so a `UserControl` `KeyBinding` inside a dialog never fires — both modals declared one and neither worked. `ShellViewModel.CloseDialogCommand` is bound to Escape on MainWindow and is **guarded by `HasDialog`**, so with nothing open the key still reaches the page (the editor drops its selection marquee on it).
- **A pill radius means "track", not "badge".** Bars (`.rt`, `.cbar`) keep 999; every badge is the `.idchip` shape (`RadiusXs`). `.hflag`, `.lockflag` and `.rtag` were capsules and are not any more.
- **A ListBox used only for virtualization must have every one of its item states neutralised.** The Set browser's unit is a *row*, which nobody selects, so Fluent's `ListBoxItem` hover, selected, pressed and focus backgrounds were a second and wider indicator under this app's own — and right-click added a ring on top. Three highlights for one row. `ListBox.tiles > ListBoxItem` sets each to `Transparent` **explicitly**; not painting a state hands it back to Fluent.
- **Parallel work goes through `Nfty.Core/ParallelWork.cs`, and only independent, non-aggregating work qualifies.** Every body must be a pure function of its own item — no shared accumulator, no running total, no appending to a shared list, no order derived from completion. Results go into a caller-owned slot per item, never collected from the loop, so the output order is the input order on any machine. **That restriction is the reproducibility guarantee**: a result that cannot depend on how many threads ran it cannot vary with core count or scheduling. Anything that *sums* stays sequential — floating-point addition is not associative, so a different order is a different number (rarity, `UniqueSpace.Count`). `ParallelWork` also unwraps `AggregateException` so the engine's own exception types and messages still reach `ErrorReport`.
- **`Generator.Generate` rolls sequentially and renders in parallel, and the split is the whole trick.** Rolling consumes one RNG stream and rejects duplicates against a running set, so the Nth asset's decisions depend on every decision before it — that phase can never be parallel and `RollAll` says so. Rendering is a pure function of a roll that is already decided, so it parallelizes freely. `GenerateStreaming` is the sequential **oracle**: `GeneratorParallelismTests` asserts the two agree on DNA, order and pixel bytes, and re-runs the whole collection at 1, 2, 3 and 8 threads to prove nothing depends on how many there are. **Measured 200 assets at 512px: 3,020 ms → 662 ms.**
- **`SetWriter` writes assets in parallel; `IngredientArchive` decodes variants in parallel.** One asset's three files depend on that asset and on a `Rarity` that is finished being built before the loop starts, so only the write ORDER changes and no reader can see it (2,078 ms → 454 ms at 512px). For archives the rule is different and sharper: **a `ZipArchive` is not thread-safe** — its entries share one stream — so extraction stays sequential and only the decode runs wide. `ArchiveIo.ReadImageBytes`/`DecodeImage` is that seam, and the variant dictionary is filled afterwards in **manifest order**, never from the parallel loop, because insertion order is observable and an order that depended on which decode finished first would vary by machine.
- **A caller's `IProgress` handler is still invoked one at a time, in increasing order.** That is a contract, not a nicety — handlers append to plain lists and update UI state, and the first parallel cut broke `Generate_reports_progress_for_each_asset` by calling one concurrently. Counting and reporting happen together inside one lock, or two threads take numbers 1 and 2 and report them in the other order.
- **Thumbnails decode off the UI thread, and `SetItemRow.Thumbnail` is null until one lands.** That is what `Border.tload` — the nfty diamond, breathing between 10% and 26% — covers. It matters at scale rather than in the demo: a thumbnail costs ~0.5 ms from a 64px source and **7.1 ms from a 1000px one**, so a screenful of forty large tiles was ~280 ms of frozen UI per scroll; decoded on the thread pool the same forty take ~27 ms. The continuation posts through `Dispatcher.UIThread.Post` rather than a captured `SynchronizationContext`, because a binding may read the property from a measure pass that has none and `FromCurrentSynchronizationContext` throws outright when there is. Tests pump until the decode lands (`PumpUntil`) rather than assuming one `RunJobs` is enough; `DecodeNow()` is the synchronous path for tests that are not about the async one.
- **Measure before optimizing: `Nfty.Core/Diagnostics/Perf.cs`.** Named scopes with wall time and managed allocation, free when off (a disabled `Perf.Measure` returns a default struct whose Dispose does nothing), on via `NFTY_PERF=1` or `Perf.Enable()`. It measures whole user-facing operations *inside the real app* — opening a Set, realizing a row of thumbnails — which is why it is not BenchmarkDotNet. `SetBrowserPerfTests` runs the 500-asset flow and prints the table; run it with `-l "console;verbosity=detailed"`.
- **What the 500-asset Set browser actually cost, and what fixed it.** Three findings, all measured, none of which changed behavior:
  - **`RowChunkConverter` rebuilt every row on every layout pass.** Its second input is the ListBox's own `Bounds.Width`, so a resize re-entered it dozens of times a second and each entry returned a *new* collection — which makes the ListBox discard and rebuild every realized container, tiles included. Eight resize steps cost **1,213 ms / 90 MB**. It now caches its last answer and returns it verbatim when the item list and the tiles-per-row are unchanged: **342 ms / 24 MB**. `A_resize_that_does_not_change_the_row_length_reuses_the_rows` asserts the identity, which is machine-independent in a way a timing assertion is not.
  - **Selection notified all 500 rows.** `OnSelectedItemChanged` set `IsSelected` on every row, so 498 of them raised a change to say "still false". Exactly two rows can change, so exactly two are touched. That is only correct because at most one row is ever selected — so `Exactly_one_row_is_flagged_selected_at_any_time` pins the invariant rather than leaving it assumed.
  - **Thumbnails decoded larger than their source.** `DecodeToWidth(fs, 128)` *upscales* a 64px asset, so a 500-tile Set of 64×64 art held four times the pixels it could use. `PngWidth` reads IHDR (bytes 16..19, big-endian) off the front of the file the decoder is about to read anyway and clamps the decode width; anything not a readable PNG returns 128, which makes the clamp a no-op and preserves the old behavior exactly.
- **The rest of a scroll is Avalonia realizing controls, not decoding images** — but that is a much smaller "rest" than it first looked, and the first reading of it was wrong in two ways worth recording so nobody repeats them.
  - **Decode is 7%** and that part holds: 182 decodes is 47 ms of ~1,500 and 1 MB of 150. Chasing image work further is chasing noise.
  - **The Fluent Button template is not the cost.** Counted, not assumed: a realized tile is **six visuals** — Button, its template's single ContentPresenter, StackPanel, Border, Image, TextBlock. Dropping the Button removes two of six, so "make a tile not a Button" is worth about a third of tile realization at most, not the 60% first claimed — and it costs focus and keyboard behavior. It is not a good trade.
  - **The benchmark was measuring a gesture nobody performs.** A wheel moves a little at a time and the virtualizing panel *recycles* containers; a jump the height of the viewport discards every one and rebuilds it. Over the same 2,400px of content: **40 wheel-sized steps warm = 32 ms / 6 MB**, the same steps cold (first realization plus decodes) = 587 ms / 36 MB, and ten viewport jumps = **1,653 ms / 149 MB**. All three are real numbers about different things; only the first two describe scrolling. `SetBrowserPerfTests` now measures both shapes and labels the jump case "worst case" so the distinction cannot be lost again.
  - Idle layout passes with nothing changed allocate **0 KB**, so there is no per-frame churn to hunt.
  - **Decode cost scales with the CANVAS the author chose, and the fixture hides it.** Per thumbnail: 2px and 64px sources both ~0.5 ms, 256px 1.0, 512px 2.3, **1000px 7.1**. The shared test fixture is 2x2, so decode measures as noise in every number above — and would in any small-pixel-art collection. It is not noise in a real one: a screen of forty 1000px tiles is ~280 ms of decoding on the UI thread each time you scroll into fresh rows. If thumbnail work is ever engineered around, THIS is the reason and the target, and the fix is to decode off the UI thread with a look-ahead — not to page the grid, which converts cheap container recycling into the expensive rebuild.
  - Cheap structural wins are still worth taking where they are free: the tile caption binds **one** class (`.tcap` muted by default, `.accent` overriding) rather than two complementary ones, because a tile is the unit this grid realizes hundreds of.
- **Tests must never read or write the real `%APPDATA%`** — inject a temp directory into `RecentsService`.
- When changing behavior, mirror the existing test style: seeded **distribution** tests for rollers, **exact-pixel** tests for colorization *and* compositing, and **round-trip** tests for archives. There are **no golden-image files** — every image assertion reads a pixel off a tiny synthetic image, so keep new imaging tests self-contained rather than introducing a golden-file harness.
- **Tests build their fixtures in memory** — each test file constructs `Loaded*` graphs directly (see `GeneratorTests.Ing`/`Recipe`/`OneRecipeBook`) from 1×1 or 2×2 solid-fill `Image<Rgba32>`s, with private per-file builders shaped for what that file tests (weights in `RarityCalculatorTests`, kinds in `KindSemanticsTests`). Tests that touch the filesystem use `Directory.CreateTempSubdirectory()`.
- **`tests/fixtures/` is the one exception**, and the only place real archives are read from disk (`FixtureArchiveTests`). `VaporPets.cbk` + its `cat.rcp`/`aura.igt` parts exercise all three layer kinds and an exclude rule in one 8×8 archive. **Their value is that an older build wrote them and they still read** — so don't regenerate them to make a failing fixture test pass; that launders a format change instead of catching it. A deliberate format change means bumping `Schema.Current` and adding a new fixture beside this one. The images are synthetic placeholders, to be joined (not replaced) by real art.
