nfty · exploration · reorder control

Surface: the Recipe detail's Layers table in explorer.html — today a read-only # / Layer / Kind / Variants / Most common table. Three ways to let an author change a layer's paint depth, each drawn twice — locked (read-only, must stay exactly as shipped) above unlocked (editing), so any column drift on unlock is visible by comparing the two. Order is bottom-to-top: depth 1 paints first, furthest back.

These are explorations, not locked. Nothing here belongs to the 1:1 reference set in docs/design/mockups/. Per the spec, one variant is promoted into the locked set and the other two are deleted.

Variant A

Per-row up / down

The idea. A trailing actions column carrying two chevrons, hidden until the row is hovered — the .rowdel idiom the Variant table already uses, and the same "append a column only when unlocked" trick ingView already performs.
The trade-off. It is the only variant that leaves every existing column exactly where it was, but a move costs one click per step, and "up" means toward row 1 — i.e. further back, so the arrow points the opposite way from the stack it moves through.

Cost + reach4 layers
Depth 4 → 13 clicks Keyboardyes Touchneeds hover Column drift on unlocknone

Watch out. Hover-to-reveal is invisible on touch and to a screen reader scanning the row. The disabled first/last buttons stay in the layout at opacity .38 so the column never reflows.

Variant B

Drag handle

The idea. A grip column prepended to the row. Press and drag; a 2 px --accent drop line (the .ramp .pin idiom) shows where the layer lands before you let go. One gesture moves any distance.
The trade-off. The landing spot is visible before commit and cost is flat, but it prepends a column so every other column shifts right on unlock, there is no keyboard path at all, and the spec explicitly puts drag-to-reorder out of scope for this pass.

Cost + reach4 layers
Depth 4 → 11 drag Keyboardnone Touchyes Column drift on unlock26 px →

Watch out. The grip glyph is the one new icon in either file — six dots, not traced from any locked mockup. And dragging up the table still means moving back in the stack, so B inherits A's direction problem in a quieter form.

Variant C

Editable depth

The idea. The # cell becomes the control: a number field (.winput geometry) with a stacked spinner. Type a depth, press Enter, the layer goes there. Out-of-range input clamps to 1..N, matching LayerDepth.MoveTo. This is the only variant that makes depth a number the author types, which is the gap the spec names.
The trade-off. Flat cost, no direction ambiguity when typing — but the column has to grow from 34 px to 88 px on unlock, and the spinner reintroduces the ambiguity in reverse: ▲ raises the number, which moves the row down the table — the exact opposite of A's up arrow.

Depth 4 → 11 entry Keyboardyes Touchyes Column drift on unlock54 px →

Watch out. One mistyped digit silently renumbers three other rows, and the row grows taller to fit the control. In Avalonia this cannot be a NumericUpDown — CLAUDE.md records that its spinner column geometry is fixed inside Fluent's template at a priority a Style setter cannot beat, so this is a bare TextBox plus two Buttons.

read it this way → The table lists depth ascending down the page, and depth 1 paints first — so the top row of this table is the back of the stack, the inverse of every layers panel an artist has used. Every ±1 affordance therefore has to pick a direction to betray. A points its arrow at the row; C points its spinner at the number; they resolve it in opposite directions, deliberately, so the two can be compared side by side rather than argued about. Hover any control for the depth transition it performs.
try it → All six tables are live and independent. Click the chevrons in A, drag a grip in B, type a depth (or a deliberately out-of-range one, to watch it clamp) in C. The moved row keeps the tr.sel highlight so you can see where it landed. Flip the theme, top right — the hover-revealed controls in A are the ones worth re-checking in dark.
